384 is the output size of all-MiniLM-L6-v2 - we're not choosing it, the embedding model dictates it.


Q: Does more dimensions = more accurate?
"Not necessarily. It's a trade-off:
Higher dims (768-1024):
Can capture more nuanced semantics
Better for complex document understanding
But: 2-3x slower search, 2-3x more memory, diminishing returns
Lower dims (384):
90% of the accuracy for our use case (trade name matching)
2x faster vector search in Qdrant
Fits 2x more vectors in RAM
For 'POLYPET' → 'PET', we don't need 768 dimensions of nuance"


Why Qdrant vs Pinecone/Milvus/Weaviate?

Why Qdrant?	"Open source, runs locally in Docker, no API keys, no network latency. Perfect for zero-budget deployment."
Why not Pinecone?	"Managed service requires API key, network calls, costs money. Violates our 'zero paid APIs' constraint."
Why not Milvus?	"Heavier, requires etcd/minio dependencies. Qdrant is single binary, simpler for MVP."
Why not pgvector?	"Good option! But separates concerns - PostgreSQL for structured data, Qdrant for optimized vector search. Qdrant has better ANN performance for high recall."


Why all-MiniLM-L6-v2 Specifically?
The Model Family Tree:

  ↓ distilled
DistilBERT (66M params)
  ↓ further optimized
MiniLM (22M params, 384d) ← We use this
  ↓ multilingual
paraphrase-MiniLM (multilingual)
Why this variant:
all-MiniLM-L6-v2: Trained on 1B+ sentence pairs for semantic similarity (our exact need)
Not distiluse-base: That one's for multilingual, we need English plastic terms
Not paraphrase-MiniLM: Optimized for paraphrase detection, overkill for trade names

HNSW = Hierarchical Navigable Small World (the algorithm Qdrant uses)
Q: Why HNSW not exact search?
"Exact cosine similarity on 10k+ vectors = O(n) slow. HNSW gives O(log n) approximate nearest neighbors with 95%+ recall. We sacrifice 2% accuracy for 100x speed."
